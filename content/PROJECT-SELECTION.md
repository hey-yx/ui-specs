# 项目选型规范

项目选型把「做什么产品」映射到「读哪套官方原文」。基准规范是这个项目唯一的数值来源，别的来源只提供原则、反例和气质。

## 三条硬规则

1. 一个项目一个基准规范：颜色、字号、间距、动效的数值不跨源拼。
2. 只认官方原文：hex、px、ms 要能在原文里读到，并连 `文件:行号` 记账。文章没有数值但有官方组件库的，用同版本官方 token 快照，快照要写变量名、值、来源文件与版本，同样按行号记账。
3. 缺口回源：基准规范没覆盖的维度按 guide 的「数值文章缺口与派生」取次源，回不到走兜底档，例外记取值记录。

## 基准规范资格

四条全过才能进表：

- 官方原文，不是二手总结或教程转述
- 数值在正文里，或来自同版本官方 token 快照（快照见下）；不是图片或组件占位符。代码仓里的 token 文件本身不进表
- 覆盖色彩、字体、间距、动效、组件里至少三类
- 每篇一个来源地址，能按行号记账

不满足的进候选池，不进基准规范表。

官方 token 快照是窄例外：只给有官方组件库、但文章正文没有数值的行用。快照放 `content/tokens/<来源>--tokens.md`，`status: partial`，正文逐条写变量名、值、来源文件与版本；文章只作原则来源。当前用于 Polaris 与 Spectrum。

## 进站方式

新卡落盘后重建即自动进站：文章页按分区生成，`catalog.json`、`search-index.json` 与 `/ai/meta.json` 都从同一份内容集合生成。项目选型点不在 `star-points.json` 里，由 `MAIN_SOURCES` 里 `files` 非空的行自动派生，所以把卡填进 `files` 就等于接上了选型。

## 现状

完整清单以 `site/src/data/guide.ts` 的 `MAIN_SOURCES` 为准，站点 `/starmap/` 的项目选型表与弹窗都从它生成。本文件只写选型规则，不再维护第二份清单。

框架与组件库看 `MAIN_SOURCES.stacks` / `libs`；图表库不跟组件库绑定，默认 ECharts，Carbon 体系用 `@carbon/charts`，纯图表页或极简需求才手写 SVG。引库锁版本，不用 latest。

## 同语境多候选怎么定

先排除不可用的：框架不匹配、没有官方组件库、项目已有体系不允许换、页面需要的组件该行没有。排除项写进 DECISIONS。

剩下的按任务形状选，不按「哪套好看」选。中文中后台、协作型工单与知识库、数据密集与值班队列、公众表单、商家后台、开发者工具各有首选。每个选型的适用场景与换用条件只写在 `site/src/data/guide.ts` 的 `MAIN_SOURCES.scenario`，站点 `/starmap/` 从这份数据生成；本文不另抄一份，避免两处漂移。

同一任务两套都成立时，用一个 brief 做 A/B：固定需求与视觉方向，只换基准规范和组件库；量 375 首个可操作对象 y、主按钮底边、1280 首屏行数、控件高度、冷启动，选密度更高、组件覆盖更全、运行成本更低的一套。品牌辨识度优先时可以选低密度方案，但要在 DECISIONS 写清代价。没做对比就下结论的，标推断，不标实测。

用户明确偏好某一版时，偏好优先于默认密度排序，但代价要写清。偏好只作用于当前项目，不上升为全局规则；在 DECISIONS 写明项目、偏好理由和放弃的指标。同类项目可参考之前的 A/B 结果，但不沿用某个项目的个人偏好。

## 版式与配色怎么核对（定稿与多站批）

这一节只在定稿核对与多站批分配时用，不作为单站生成的前置步骤。单站生成时结构交给 Hallmark，按产品动作定，不先选 nav/footer 三件，也不为了凑候选另出页面。

版式按产品动作挑，不按「安全」挑。默认组合是模板指纹，先当淘汰项：应用页的 Workbench + N1b + Ft3，营销页的 Marquee Hero + N1b + Ft1。只有产品确实没有第二种结构可用时才留，并在取值记录里写清其余件为什么不合身。

- 多站批开批前才出两套候选（版式骨架 + 强调色 + 首屏落点），写下淘汰另一套的理由，再定；单站不先做这件事。候选只写进取值记录，不另出第二份页面文件。
- 骨架里至少一件要承担产品自己的动作，例如柜格、队列、票据、时间轴、地图。件件都是中性容器就是没挑。
- 选件理由写「产品动作 ↔ 版式定义」一句，不写安全、稳妥、用户熟悉。
- 强调色在该项目的基准规范色板里取，写 `文件:行号`，不跨源借色。
- 版式件名与选用标准见 `briefs/layouts.md` 的速查表，件名以 Hallmark 版式库为准；规则以本节为准，速查表只做索引。

## 选型流程

1. 定语境：产品做什么、给谁用、表单还是图表、有没有既有品牌要复刻。
2. 定基准规范：同语境有多套体系时按项目实际情况选一行，例如政务服务暂无内置行（原英国与美国两套已于 2026-11-13 移除），按需求另定；选定后整套值都从这一行取，不跨行混用。需求开了框架的，只在有该框架官方组件库的行里选，选不到就换行。同语境多候选先按框架、既有体系与官方组件库排除，再按任务密度、首屏目标、组件覆盖与运行成本比，不按视觉偏好选。具体首选与换用条件见 `MAIN_SOURCES.scenario` 与站点 `/starmap/` 的选型表，本文不重复。对比至少量 375 首个可操作对象与主按钮位置、1280 首屏行数、控件高度和冷启动；候选、排除理由与实测写进 DECISIONS 或 FINDINGS，没量过的标未知。
3. 读基准规范：从基准规范的文章里取 3 到 5 个关键值，连 `文件:行号` 记进取值记录。
4. 补缺口：基准规范缺的维度回源取次源，回不到走兜底档，写进 FINDINGS。
5. 回炉：出稿后按设计点复测，值对不上引用行就重取。

## 新增官方基准规范

1. 在官方文档仓或官方站确认四条资格，先看数值是不是真在正文里。
2. 按 `content/README.md` 的配方收文，一节一文件，色彩、字体、布局、动效分开落分区。
3. 在 `MAIN_SOURCES` 加一行：`context`、`id`、`short`、`source`、`files`、`note`，有官方 React 或 Vue 组件库的再填 `stacks`（框架加 npm 包名）。`id` 显式写，别靠基准规范名派生，同一基准规范多语境会撞 id。图表库不进 `stacks`，按上文的默认 ECharts 或 Carbon 体系走。
4. 跑 `npm run build`：文章不存在会让构建失败；项目选型点由 `MAIN_SOURCES` 自动派生，出现在设计地图、`/ai/design-points.json` 与 guide 对照表里，不用再改 `star-points.json`。新收的文章只放文件不填进任何点的 `articles` 或 `files` 时，构建会以「文章未被牵引」拦下。
5. 更新 `MAIN_SOURCES` 与本规范；选型清单不在本文另抄一份，站点从 `MAIN_SOURCES` 自动生成。

代码仓里的 token 文件不当文章收：那种文件没法带行号记账，也不能当叙述依据。

## 用 Hallmark 抽外部站点

复刻某个站点，或目标站没有公开设计系统时走这条线。

1. Hallmark 识别目标站：色板、字阶、间距、圆角、阴影、动效、组件语言、密度。
2. 落卡：`content/brands/designmd--<域名>.md`，frontmatter 八个字段照 `content/README.md`，`source` 写站点地址，`fetched` 写识别日期，`publisher` 写站点名加「站点抽取」。
3. 正文按 DESIGN.md 骨架写：
   - 概览：产品类型、气质一句话
   - 色板：hex 加用途
   - 字阶：字号、行高、字重
   - 间距与圆角：px 表
   - 动效：时长与缓动
   - 组件语言：按钮、卡片、表单的形状与状态
   - 可访问性：对比度实测结果
   - 边界：适合复刻什么，不适合什么
4. 在 `MAIN_SOURCES` 加一行：`context` 写「复刻 <站点>」，`id` 写 `project-<域名>`，`files` 指向刚落的卡。只落卡不填行时，构建会以「文章未被牵引」失败；填进 `files` 后重建，项目选型点自动生成。
5. 验收：抽 3 到 5 个关键值回原站复核，截图存证，证据等级标 derived。
6. 记账：取值记录引用写 `content/brands/designmd--<域名>.md:行号`。

抽取结果只服务这一个项目，不并进其他项目，也不拿来当通用规范。同一个站再抽取时覆盖旧卡，不并排留两份。

## 候选池：2026-11-07 GitHub 核查

- Ant Design：`docs/spec` 有七十多篇中文规范页，价值观、色彩、字体、布局、动效、对比度、暗色、图标、文案都有，但色板与字阶由组件和图片渲染，hex 与字号取不到，暂不进基准规范表。
- Arco Design：`site/docs_spec` 以组件规范为主，同样取不到数值。
- Semi Design：Token 文档由组件渲染，数值不在 Markdown 里。
- Fluent 2：官方站是 JS 渲染，仓库里只有组件与架构文档，没有规范正文。
- Base Web、Gestalt：文档在仓库，内容以组件用法和文案规范为主，数值项待核查。

结论：仓库里能直接当基准规范用的没有。要数值就走站点抽取路线，或者等官方站可抽取时再收。
