# FINDINGS · ListenRail（listenrail）

## 1. 本稿相对合格线的落点

全部为可复核的实测事实，环境为 Chromium（Hermes browser harness）打开 `file://` 本地文件，无网络。

- 四档宽度均无横向滚动：320 → `320/320`，375 → `375/375`，768 → `753/753`，1280 → `1265/1265`（后两档的 15px 差是滚动条，`scrollWidth === clientWidth` 成立）。
- 外部资源 0 个：`performance.getEntriesByType('resource').length === 0`；无 CDN、无外链字体、无外链图片，封面是运行时生成的内联 SVG。
- 行高：103 个含直接文本的节点，四档各普查一次，违例 0（验收标准 `computed lineHeight === fontSize + 8`，容差 0.6px）。
- 强调色实填面积：1280 `0.25%`、768 `0.39%`、375 `1.53%`、320 `1.44%`，均低于 5%。
- 对比度（WCAG 公式现算，半透明先合成）：标题 17.49:1；正文与说明 5.74:1；浅灰底元信息 5.56:1、面板标签 5.17:1；按钮白字 6.54:1（hover 9.40、active 12.95）；禁用态 4.95:1；错误文案 6.31:1；成功文案 6.50:1；深色条次要文字 6.90:1。
- 非文本对比度：输入框描边 3.41:1、浅灰底描边 3.07:1、焦点环 6.54:1，均 ≥ 3:1。纯装饰的发丝线 1.23:1、引号 1.88:1 不承担任何识别任务。
- 触控目标：播放键 44×44、筛选块高 44、主按钮与输入框高 48、平台行高 64，≥ 44px 下限。
- 首屏占比：hero 765px / 视口 900px = 85.0%，下一节露头不到一屏。
- 交互全部实测通过：筛选 8 → 5 → 3 → 8；表单空值 / 格式错 / 成功三态；播放 2.1 秒后计时 `00:02`、进度 `scaleX(0.0008)`（第 32 期 2772 秒）；切台复位；暂停回位；首屏「从这一期开始听」起播第 1 行并把焦点送到该行播放键。
- 键盘序完整：跳过链接 → 品牌 → 往期 / 听友 / 关于 / 订阅 → 邮箱 → 订阅 → 从这一期开始听 → 平台链接。
- `prefers-reduced-motion: reduce` 下实测 `transition-duration: 0s`（关闭而非变慢）。

## 3. 新缺口

指南没有覆盖、本稿被迫自行决定的维度，按「是否建议回填」排列。

1. **强调色实填面积没有计算口径。** 「< 5%」没说算不算文字色、算不算描边、算不算 hover 态。本稿采用「`background-color` 等于强调色的元素矩形面积之和 ÷ 文档面积」，实测 0.25%–1.53%。建议回填：写清是否含文字、是否含描边与阴影，否则同一页面可以算出 0.3% 和 8% 两个数。
2. **列表行没有规格档。** 「组件尺寸」只提输入框、表格行高；播客列表这种「播放键 + 封面 + 两行文字 + 右对齐时长」的行，行内 padding、封面尺寸、时长列对齐都没有参照。建议补一行「列表行（非表格）」的成套尺寸。
3. **内容卡片容器的内距没有来源。** 「最新一期」面板用了 24px 内距、8px 圆角、浅灰底，三项分别来自间距尺度与圆角派生档，但「卡片容器用什么内距」本身没有原文。建议在组件尺寸条里补一条容器内距档。
4. **进度条 / 数据型动效不属任何时长档。** 基准规范三档讲的是转场与微观变化；播放进度是数据更新，加过渡反而有延迟感。本稿选择不加过渡（瞬时更新），这是一个没有原文依据的判断，建议指南给「数据更新不做补间」这类负向规则。
5. **中文行内断词无实现手段。** 库里有 clreq 文章（`content/standards/w3c--clreq.md`），但 CSS 只能约束标点禁则，无法阻止「改过的 / 主意」这种词内断开。视觉评审两次把它当缺陷报。建议指南明确：中文词内换行属正常排版，不作为验收项，或给出可用的 `line-break` / `word-break` 组合口径。

## 4. 已知局限

- **播放是模拟的。** 计时基于 `performance.now()`，刷新即归零，不记忆进度，没有音频解码，进度条只是视觉反馈。页脚已写明「播放是模拟的，不会真的响」。
- **平台链接指向平台首页**，不是本节目主页——没有真实节目 ID 可接，需求也明确不接平台 API。
- **订阅没有后端。** 成功只改前端状态（按钮禁用 + 绿字回显 + 输入框只读），刷新失效，邮箱没有被发送到任何地方。
- **只在 Chromium 测过。** Safari / Firefox 的 `text-wrap: balance`、`overflow-x: clip`、`svh` 表现未实测；`text-wrap: balance` 在旧版浏览器会退化成普通换行，不影响可读性。
- **后台标签页的计时不可信。** 首个版本用 `requestAnimationFrame`，页面 `visibilityState === 'hidden'` 时完全不触发；改 `setInterval(200ms)` 后隐藏态仍被节流到约 1 次/秒，实测 2.5 秒只推进约 1.9 秒。本文件里的播放数字都是 `Page.bringToFront` 之后前台重测的。
- **无障碍只做了可程序化验证的部分**：对比度、行高、键盘序、`aria-pressed` / `aria-invalid` / `aria-live`、reduced-motion。没有跑 VoiceOver / NVDA，焦点陷阱（本页无弹层）未涉及。
- **单字段表单没做 GOV.UK 式 error summary。** `content/patterns/govuk--validation.md:67` 要求错误摘要 + 焦点移过去；本页只有一个字段，采用内联错误 + `aria-invalid` + 焦点回填，是一处有意偏离，写在这里而不是当成合规。
- **没有深浅色切换。** 读了 `content/color/tdesign.tencent.com--dark.md`，只把「白字 60%」用在深色订阅条上，全站仍是单一浅色主题。
- **封面是程序化装饰，不承担识别。** 8 张封面按 5 种构图轮换，同构图的期数看起来接近；识别依赖标题与期号。
